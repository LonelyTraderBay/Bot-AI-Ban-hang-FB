# FE012 — Route / operation map

Scope is the React/TypeScript frontend under `apps/web` with the synthetic MSW API. Canonical inputs are `botsales-kit/contracts/route-manifest.json`, `openapi.json`, `permission-catalog.json`, and the generated operation registry. The executable source map is `tests/fe012-source-map.test.mjs`.

| Route | Reads and owner | Actions and permission boundary | Notes |
|---|---|---|---|
| R17 `/s/:shopId/orders` | `OrdersPage` reads `listOrders`; URL-backed search/pagination come from shared filters. Rows show order, fulfillment, and payment states separately and link to R19. | Create link requires `orders.write`. | Totals are API snapshots; the page does not sum paginated rows into shop revenue. |
| R18 `/s/:shopId/orders/new` | `DraftForm` searches `listCustomers(q)` and `listProducts(q)` under `customers.read` / `catalog.read`; `listConversations` is optional, customer-scoped, and requires `conversations.read`. `getShop` is supplied by `Shell` session scope. | `createOrder` / `updateOrderDraft` require `orders.write`; inputs preserve contract IDs, unique variants, integer quantity 1–1,000,000, at most 100 lines, and notes up to 2,000 characters. | Quote/totals and stock are server-authoritative. Address CRUD is absent; the UI accepts only an externally verified `shippingAddressId` and warns that the mock does not verify a real address. |
| R19 `/s/:shopId/orders/:orderId` | `OrderDetailPage` reads `getOrder`. | `quoteOrder`, `cancelOrder`, and edit actions require both permission and the matching `allowedActions`; confirmation additionally requires `orders.confirm` and action `confirm`; observed payment/refund use `finance.post` / `finance.refund` and `record_payment` / `request_refund`. | Quote refreshes `getOrder` so action availability follows the server. 202 commands wait for terminal state; unknown commands remain under shared `getCommand` recovery. Preparation links to fulfillment; shipment handover remains owned by its existing fulfillment route and `fulfillment.handover`. |
| R43 `/s/:shopId/returns` | `ReturnsPage` reads `listReturnCases`, then fetches `getReturnCase` before inspection. Orders are loaded only with `orders.read`. | `createReturnCase` requires `orders.return`; `inspectReturn` requires `inventory.adjust` and sends the current case version. | Return quantities and inspection values are validated; the API decides cumulative eligibility. A received synthetic case exercises partial acceptance. Only accepted sellable quantity adds mock stock, and refund obligation is calculated from accepted quantity. |

Shared API behavior is grounded in the registered operations and hooks: request schemas, If-Match/expected version, CSRF and idempotency metadata, 202 completion polling, and unknown-result recovery. `handoverShipment`, `getCommand`, and `getShop` are intentionally mapped to their existing fulfillment, recovery, and Shell owners rather than duplicated in the order module.

Explicit limits: frontend acceptance uses synthetic users, orders, inventory, and payment evidence only. No address endpoint or verified address is invented. The demo customer-confirmation action is synthetic and cannot establish real customer consent. `ReturnCaseResponse` does not expose accepted quantity as a distinct field; the mock retains requested line quantity and returns the calculated refund obligation.
